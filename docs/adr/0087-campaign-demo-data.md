# ADR-087: Campaign-level demo data, generated daily and superseded (not replaced) on reseed

## Status

Accepted (EX-3).

## Context

Experiments (T-038, spec §25) are meant to compare campaign vs. campaign, but the demo dataset
(spec §27) only ever wrote one spend/conversions fact per leaf budget per month — there was no
`campaign` dimension value on any demo fact, and no demo experiment at all. A reviewer (or the
owner, in the production "Sandbox" workspace) could not exercise the campaign-comparison UI without
first loading their own data.

The `campaign` registry dimension already existed (T-001–T-005, `packages/db/seed/defaults.registry.ts`),
org-scoped like `region`/`country`/`platform`, with no seed values (real campaign ids are source- or
client-specific). Demo campaign codes needed to be invented, and needed to not collide with another
demo workspace's campaigns sharing the same org-wide dimension.

EX-2 (built in parallel, campaign-experiments.md) adds fact-scoped filter evaluation to the planner.
To avoid a build-order dependency, the one demo experiment this item adds uses the *existing*
Experiment schema (`testFilter`/`controlFilter` as envelope-scoped FilterGroups) with a filter on
`{kind:"dimension", key:"campaign"}`. Until EX-2 lands, that filter scopes nothing (envelopes do not
carry `campaign` in their tuple, by design — see below); EX-2's migration maps existing
campaign-equality filters onto its fact scope, so this experiment starts reading real numbers
without anyone touching it again.

## Decisions

1. **Campaigns are fact-only, never part of an envelope's tuple.** A budget (envelope) stays at the
   platform/objective/audience granularity; `campaign` rides in `dimension_values` only on
   `spend_fact`/`kpi_fact` rows. `matchRunFacts`'s existing subset match
   (`envelope.dimension_values <@ fact.dimension_values`) needs no change: a fact tagged with a
   campaign still matches its leaf envelope, because the envelope's tuple remains a subset.
2. **Campaign codes are workspace-qualified** (`<first-8-hex-of-workspace-id>_<label>`) so the
   org-wide `campaign` dimension's `(dimension_id, code)` uniqueness never collides between two demo
   workspaces (or a demo workspace and real data) in the same org. Labels stay realistic and
   unqualified, e.g. `BR_Meta_Prospecting_Q4_VideoA`.
3. **Daily, not monthly, facts**, generated by a deterministic hash-based generator (no new
   dependency — it's under 40 lines): per leaf, per month, the same `85…105% of the monthly plan`
   total the old generator used is split across that month's *active* campaigns (weighted,
   renormalized when one has not started yet) and its days (±20% jitter). A small fraction of
   (leaf, campaign, day) combinations are dropped entirely — never written as a zero-amount row —
   to represent a paused campaign ("no data" per the owner's requirement that a day with nothing
   never shows as zero or gets interpolated). Exactly one campaign, the last one on the first leaf,
   starts midway through the window instead of on day one.
4. **Consequence, accepted:** because the current (open) month only gets facts for its *elapsed*
   days — the old generator wrote the whole month's amount on day 1, regardless of how much of the
   month had passed — a leaf's total across the whole fiscal-year-to-date window is close to but a
   little under the old monthly total. Closed months (every day present) are unaffected. This is
   realistic (actuals, not a forecast placeholder) and is covered by a documented tolerance in
   `packages/db/src/demo.test.ts`, not an exact-total assertion.
5. **Reseeding an existing workspace never deletes the old monthly facts.** `reseedCampaignDemoData`
   (`POST /workspaces/:ws/demo-data/campaigns`, org admins only) writes the new campaign-level facts
   under a fresh `source_run_id`, then marks every live demo fact of the same leaves that has no
   `campaign` key as `superseded_at = now()` by hand (ADR-071's mechanism, applied directly since the
   demo "source" has no `ingest_run`/`source_id` for `supersedeUnseenFacts` to key off). Idempotent:
   if the workspace already has live, campaign-tagged demo facts, the call is a no-op and nothing is
   audited. This is how the production Sandbox (seeded before this change) picks up campaign-level
   data without the owner running anything by hand against it.
6. **`Experiment` gets a `demo` boolean** (migration `20261020030000_experiment_demo_flag`), matching
   `Envelope`/`EnvelopeVersion`/`Target`/`TargetVersion`, so `purgeDemoData` can find and delete it
   and the reseed endpoint can tell its own demo experiment already exists.
7. **Purge deletes the campaign dimension's values too, but only when nothing else uses them**: since
   the `campaign` dimension is org-wide, another workspace's real campaign could in principle (not in
   practice, given the workspace-qualified codes) share a code; the purge checks for any other live
   fact referencing each code before deleting its `dimension_value` row.

## Consequences

- A brand-new demo workspace is fully experiment-ready immediately; no separate step.
- An existing demo workspace (notably Sandbox) needs one org-admin click (Settings › Workspace ›
  Demo data › "Add demo campaign data") or API call to catch up.
- The demo experiment is inert (its filter scopes nothing) until EX-2 ships; this item's PR says so
  explicitly so the reviewer isn't surprised the readout shows no numbers yet.
